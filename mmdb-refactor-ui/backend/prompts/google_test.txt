## Google Test Style Guide (MMDB)

### Core principle: no mocking — use real data files

Do NOT construct synthetic in-memory structures (e.g. manually building an
`mmdb::Manager` by hand) unless the function under test is completely
trivial and requires no real molecular data.

Instead, load a real PDB or mmCIF file from disk and let MMDB parse it.
This ensures the test exercises the function against realistic, well-formed
data.

### Loading data

Read a PDB / mmCIF file via the manager — this is the only loading pattern
you should use:

```cpp
mmdb::Manager mgr;
int rc = mgr.ReadCoorFile("path/to/test.pdb");
ASSERT_EQ(rc, mmdb::Error_NoError) << "Failed to read PDB file";
mmdb::Model* model = mgr.GetModel(1);
ASSERT_NE(model, nullptr);
```

The test data file path should be expressed as a compile-time constant or
passed via a command-line argument / environment variable so the test is
portable:

```cpp
static const char* TEST_PDB = TEST_DATA_DIR "/test.pdb";
```

### Establishing expected values: use the oracle output

Do NOT guess or hardcode expected output values. The probe oracle has
already run the function on a real PDB file and captured its output —
those measured values are provided to you in the prompt as `PROBE: ...`
lines. Assert against THOSE numbers, not numbers you make up.

Pattern for a function that returns a value:
```cpp
mmdb::Manager mgr;
ASSERT_EQ(mgr.ReadCoorFile(TEST_PDB), mmdb::Error_NoError);
auto result = function_under_test(mgr.GetModel(1), ...);
EXPECT_EQ(result, /* value from PROBE: line in the prompt */);
```

Pattern for a function that modifies a structure in-place:
```cpp
// Run the function, then assert the observable post-state matches the
// PROBE: lines from the oracle.
```

### What the test should do

1. Load the data file (assert success).
2. Obtain the relevant sub-object (model / chain / residue / atom) the
   function needs, by walking the mmdb hierarchy with `GetModel`,
   `GetChain`, `GetResidue`, `GetAtom`.
3. Call the function under test with those real inputs.
4. Assert the output matches the PROBE: lines using `EXPECT_EQ` /
   `EXPECT_NEAR` / `EXPECT_STREQ`.

### Forbidden patterns

- `MOCK_METHOD` / gmock stubs for molecular objects.
- Manually calling `mmdb::Model::AddChain`, `AddResidue`, `AddAtom` etc. to
  build a fake structure from scratch (unless the function itself is a
  constructor / builder).
- Hardcoding atom coordinates, residue names, or expected return values as
  magic numbers — derive them from the PROBE: lines.
- Any reference to gemmi: no `gemmi::` types, no `#include <gemmi/...>`,
  no `gemmi::read_structure_file`. The MMDB test must be pure MMDB.
- `using namespace mmdb;` — every type must be qualified `mmdb::Foo`.

### TEST naming

```cpp
TEST(FunctionNameTest, DescriptiveScenario) { ... }
```

Use one `TEST` block per logical scenario. Keep fixture classes (`TEST_F`)
only when multiple tests share the same file-loading setup.
